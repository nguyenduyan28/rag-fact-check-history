# Compare Our Project With HisGraphRAG

Reference notes:

- HisGraphRAG summary: `docs/GraphRAG/idea.md`
- Our pipeline summary: `docs/Ours/idea.md`

## Short Comparison

| Aspect | HisGraphRAG | Our Project |
|---|---|---|
| Main task | Multiple-choice Vietnamese history QA | Vietnamese history claim verification |
| Input question type | MCQ question with 4 answer options | Declarative claim with `real/fake` label |
| Main corpus | Grade 12 Vietnamese history textbook | Grades 10, 11, 12 textbook OCR chunks plus QA-derived claims |
| Retrieval style | GraphRAG with entities, relations, temporal retrieval | Hybrid BM25 + BGE-M3 dense retrieval with RRF |
| Knowledge structure | Neo4j graph, SQL temporal DB, Milvus embeddings | Text chunks only, no explicit graph |
| Main innovation | Entity alignment, answer candidate filtering, temporal retrieval, reranking | Dataset construction + blind/RAG fact-checking benchmark |
| Evaluation | Accuracy on VUEE 2017/2018 MCQ QA | Accuracy, precision, recall, F1 on real/fake claim verification |
| Best reported result | HisGraphRAG: 81.7% / 70.8% on VUEE 2017/2018 | Blind LLM: 84.81%; RAG verification: 75.80% |

Important:

> Do not present our method as a direct improvement over HisGraphRAG unless we run the same MCQ QA benchmark. Our current task is different.

## What HisGraphRAG Does Better

HisGraphRAG has a clearer method contribution:

- It builds an explicit entity-relation graph.
- It handles duplicate historical entities with entity alignment.
- It uses time-aware retrieval for history questions.
- It filters answer choices before retrieval.
- It uses reranking before final answer generation.
- It reports ablations showing which component helps.

HisGraphRAG also has a cleaner paper story:

> Basic RAG is weak for historical QA because history needs entities, relations, chronology, and option-aware reasoning. HisGraphRAG adds those pieces.

Our current story is less sharp because it mixes:

- dataset construction
- claim generation
- fake claim generation
- blind LLM verification
- RAG retrieval
- RAG re-verification

That can become a strong paper, but only if the contribution is framed clearly as a **Vietnamese history claim-verification benchmark**, not as another GraphRAG paper.

## What Our Project Does Differently

Our project has a different opportunity:

- HisGraphRAG asks: "Can we answer exam questions better?"
- Our project asks: "Can we verify Vietnamese historical claims using evidence?"

This is valuable because claim verification is closer to fact-checking and misinformation detection.

Our possible novelty:

- Build a Vietnamese historical claim verification dataset.
- Include both textbook-derived claims and exam-derived claims.
- Include real and controlled fake claims.
- Compare blind LLM verification with evidence-grounded RAG verification.
- Analyze how retrieval quality affects real/fake judgment.

This can be positioned as:

> A benchmark and analysis paper, not only a system paper.

## Mistakes Or Wrong Ideas In Our Current Project

### 1. Calling It GraphRAG Would Be Wrong

Our current RAG is not GraphRAG.

It does not extract entities, build graph nodes/edges, align entities, or traverse a graph. It is hybrid text retrieval:

- BM25
- dense embedding search
- RRF fusion

Better wording:

- "hybrid RAG"
- "retrieval-augmented claim verification"
- "evidence-grounded LLM verification"

Avoid:

- "GraphRAG" unless a graph is actually implemented.

### 2. Comparing Accuracy Directly With HisGraphRAG Is Misleading

HisGraphRAG evaluates MCQ QA. Our project evaluates binary claim verification.

These are not the same:

- MCQ QA has answer-option competition.
- Claim verification has binary classification.
- HisGraphRAG's wrong answer options are part of reasoning.
- Our fake claims are generated data and may contain artifacts.

Better comparison:

- Compare pipeline design, retrieval assumptions, and evaluation weaknesses.
- Do not compare headline accuracy as if both solve the same benchmark.

### 3. Our Fake Claims May Be Too Easy Or Too Artificial

Fake claims are generated by LLM transformations:

- number/date manipulation
- entity substitution
- event reversal
- information addition/removal

This is useful, but risky. The model may detect artificial writing patterns instead of checking history.

Paper fix:

- Add human validation on fake claims.
- Report fake-claim type distribution.
- Evaluate per fake type.
- Add adversarial hard negatives that are close to true evidence.
- Include naturally occurring wrong answer claims from exams as a separate subset.

### 4. The Dataset Is Imbalanced

Current final dataset:

- fake: 6504
- real: 2218

This means fake is about 74.6% of the data.

Mistake:

- Reporting only accuracy can make a fake-biased system look good.

Paper fix:

- Report macro F1.
- Report balanced accuracy.
- Report real recall and fake recall.
- Report per-source metrics.
- Consider balanced test sets.

### 5. Evidence Quality Is Not Stable Across Sources

The `v2` subset has evidence from textbook/event data.

VNHSGE and VMLU are QA-derived. Their evidence may be empty, generated later, or retrieved by RAG.

Mistake:

- Treating all claims as if they have equal evidence quality.

Paper fix:

- Split results by source:
  - textbook-derived claims
  - VNHSGE-derived claims
  - VMLU-derived claims
- Split by evidence type:
  - gold/source evidence
  - empty evidence
  - retrieved evidence
  - noisy OCR evidence

### 6. RAG Retrieves Top 5 But Verifies With Only Top 1

`rag.py` retrieves top 5 documents.

`verify_rag.py` uses only:

```python
relevant_rag = item["relevant"][0].get("text", "")
```

Mistake:

- This throws away 4 retrieved passages.
- If the first passage is only topically related, the verifier may fail.

Paper fix:

- Test top-1, top-3, top-5.
- Add LLM reranking like HisGraphRAG.
- Ask the verifier to cite which passage supports or refutes the claim.

### 7. Retrieval Is Not Evaluated Directly

Current RAG result only measures final real/fake classification.

Mistake:

- We cannot tell whether failure comes from retrieval or verification.

Paper fix:

- Manually label retrieved evidence relevance for a sample.
- Compute Recall@k or Hit@k if gold evidence exists.
- Compare BM25 only, dense only, and BM25+dense RRF.
- Measure whether gold evidence appears in top-k.

### 8. OCR Noise Can Become A Hidden Variable

OCR chunks include noisy text. Some examples contain broken Vietnamese words or distorted map/table text.

Mistake:

- Treating OCR corpus as clean textbook text.

Paper fix:

- Report OCR/text-cleaning method.
- Measure retrieval and verification separately on clean vs noisy chunks.
- Remove figure/map OCR noise or tag it separately.

### 9. Source Field Is Missing In The Final Dataset

`data/final_dataset.json` currently has:

- `ID`
- `key`
- `claim`
- `relevant`
- `label`

It does not include `source`.

Mistake:

- This makes it harder to reproduce `v2` vs `vnhsge` vs `vmlu` results.

Paper fix:

- Add `source` to every row.
- Add `origin_question_id` or `origin_event_id`.
- Add `fake_type` for generated fake claims.
- Add `evidence_type`.

### 10. Reproducibility Needs Work

Problems found:

- Some scripts use absolute paths under `/home/khoa/Documents/GitHub/...`.
- `4.rag/src/rag.yaml` points to `data/4.rag/final_dataset.json`, but that file is missing.
- `3.Verify/pipeline.py` imports `config`, but `3.Verify/config.py` is not in the repo.
- Reported dataset size is inconsistent: 9185 in report vs 8722 in current final files.

Paper fix:

- Make all paths relative to repo root.
- Add config files or document generated/private configs.
- Add one reproducible command per experiment.
- Freeze dataset version used for paper tables.

## What We Can Borrow From HisGraphRAG

### 1. Entity Alignment

Our keys and evidence likely contain duplicate entities:

- "Liên Xô"
- "Liên bang Xô viết"
- "Soviet Union"

Borrowing entity alignment could improve:

- grouping claims by event
- retrieval queries
- duplicate detection
- source-specific EDA

### 2. Temporal Retrieval

History verification often depends on time.

Our fake claims often manipulate dates, so temporal retrieval is especially relevant.

Useful addition:

- extract years/dates from claims
- retrieve textbook chunks near the same period
- detect contradictions like wrong year, wrong sequence, wrong period

### 3. Reranking

HisGraphRAG reranks retrieved context before answering.

Our RAG should add:

- top-k retrieval
- reranking
- final verification over selected evidence

This is probably the easiest high-impact system improvement.

### 4. Ablation Study

HisGraphRAG is stronger as a paper because it compares variants.

We need ablations:

- LLM-only claim verification
- gold evidence verification
- BM25-only RAG
- dense-only RAG
- BM25+dense RRF
- RRF + rerank
- RRF + temporal filtering
- top-1 vs top-3 vs top-5 evidence

## How Our Paper Could Be Stronger Than HisGraphRAG

HisGraphRAG focuses on answer accuracy. Our paper can focus on **why systems fail**.

Good analysis angles:

- Does RAG help real claims more than fake claims?
- Does generated fake type affect verification?
- Are date-change fakes easier than entity-substitution fakes?
- Does OCR noise reduce retrieval quality?
- Does the model over-trust retrieved evidence?
- Are exam-derived claims harder than textbook-derived claims?
- Does `key + claim` retrieval outperform claim-only retrieval?

This kind of error analysis can make the paper more convincing even if the system is simpler than HisGraphRAG.

## Suggested Paper Direction

Best current framing:

> We present a Vietnamese historical claim verification benchmark built from textbook evidence and exam-style QA data. We evaluate blind LLM judging and hybrid retrieval-augmented judging, showing that retrieval improves some real-claim verification behavior but introduces false positives when retrieved evidence is topically related but not decisive.

Possible title ideas:

- `ViHistFact: A Vietnamese Historical Claim Verification Benchmark`
- `Evidence-Grounded Verification of Vietnamese Historical Claims`
- `From Exam Questions to Historical Claims: Building a Vietnamese Fact Verification Benchmark`

## One Strong Method Upgrade

The best next system idea:

> Add a temporal and entity-aware reranking layer before verification.

Pipeline:

1. Extract entities and time expressions from the claim.
2. Retrieve top 20 chunks with BM25 + dense.
3. Score chunks by:
   - semantic similarity
   - entity overlap
   - temporal overlap
   - keyword overlap
4. Rerank to top 3 or top 5.
5. Ask the LLM to verify with explicit evidence citation.

This borrows the useful parts of HisGraphRAG without needing to build a full graph immediately.
