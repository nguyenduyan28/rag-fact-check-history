## Problem

Stage 5 extracts useful entities, but each entity is local to one chunk. The same historical entity can appear in many forms.

Examples:

```text
Mỹ / Mĩ / Hoa Kỳ
Liên Xô / Liên bang Xô viết
Nguyễn Ái Quốc / Hồ Chí Minh / Nguyễn Tất Thành
An Nam / Việt Nam / Đại Việt
```

If these variants are not aligned before graph construction, Stage 7 would create duplicate nodes. That would fragment graph retrieval because evidence stored under one alias may not connect to a claim using another alias.

## Method

Method name:

```text
Deterministic entity normalization with targeted Gemini alias review
```

The implemented method has four parts:

1. Collect all entity mentions from cleaned Stage 5 output.
2. Deterministically normalize and collapse exact duplicate `(type, normalized_name)` entities.
3. Generate high-value fuzzy candidate groups for alias review.
4. Ask Gemini to review only those candidate groups, then apply accepted merges.

Gemini is intentionally not used for every possible entity pair. It only reviews candidate groups generated by local rules. This keeps cost bounded and reduces bad merges.

## Deterministic Normalization

The deterministic stage applies:

1. Unicode NFC normalization.
2. Lowercasing for comparison keys.
3. Punctuation cleanup.
4. Whitespace normalization.
5. Vietnamese accent folding for candidate discovery.
6. Exact `(type, normalized_name)` grouping.

This step is safe because it only merges identical normalized names within the same entity type.

## Candidate Group Generation

The code does not send all entities to Gemini. It builds a bounded list of candidate groups.

Configured limit:

```yaml
entity_alignment:
  max_candidate_groups: 300
```

The cap is applied in `build_candidate_groups()`:

```python
return deduped_groups[:max_candidate_groups]
```

This means:

```text
All entities are included in final output.
Up to 300 fuzzy/uncertain candidate groups are reviewed by Gemini.
```

Candidate group sources:

1. Seed alias groups, such as `Mỹ / Mĩ / Hoa Kỳ`.
2. Folded-name groups, such as accent or spelling variants.
3. High-similarity token/name groups.

The broad country-state sliding window is disabled by default because it created many loosely related groups.

## Why The Run Uses 300 Groups

The first completed Gemini review used 150 candidate groups. After review, we broadened candidate generation and reran Stage 6 with a 300-group cap.

The 300-group setting is a controlled quality improvement, not full pairwise matching.

Reasons:

1. Full pairwise entity comparison would be expensive.
2. Fuzzy candidate generation can produce many weak groups.
3. Bad merges are worse than missed merges because they corrupt canonical graph nodes.
4. The highest-priority groups are processed first: seed aliases, folded-name groups, then similarity groups.
5. Exact normalized merging already handles all obvious same-name duplicates.

Reasons:

1. It reviews more fuzzy aliases than the initial 150-group run.
2. It avoids full all-pairs matching over 3742 representatives.
3. It enables country/state windows for aliases like `Mỹ`, `Pháp`, `Nhật Bản`, and `Liên Xô`.
4. It lowers the similarity threshold enough to catch more variants while still keeping a cap.

Full pairwise comparison would require roughly:

```text
3742 * 3741 / 2 = 6,999,411 possible pairs
```

That is too expensive and too risky for automatic Gemini merging.

Current controlled setting:

```yaml
max_candidate_groups: 300
similarity_threshold: 0.85
enable_country_state_windows: true
```

These are not blindly merged by rules. They become Gemini review candidates because some are context-dependent.

Examples:

1. `Nguyễn Ái Quốc`, `Hồ Chí Minh`, and `Nguyễn Tất Thành` can refer to the same person.
2. `An Nam`, `Việt Nam`, `Đại Việt`, and `Đại Cồ Việt` are related historical names but should not always become one node.
3. `Pháp`, `thực dân Pháp`, and `đế quốc Pháp` may refer to country, colonial force, or imperial actor depending on context.

## Gemini Review

Gemini receives one candidate group at a time and must return JSON only.

The prompt tells Gemini to:

1. Merge only names that refer to the same historical entity.
2. Not merge entities only because they are historically related.
3. Avoid cross-type merges except clear extraction-type mistakes.
4. Keep `Event` separate from `Organization`, `Place`, and `Person`.
5. Mark uncertain cases as `review_required=true`.
6. Use `confidence >= 0.80` for automatic merges.
7. Preserve original names as aliases.

Gemini config:

```yaml
entity_alignment:
  provider: gemini_vertex
  model: gemini-2.5-flash
  temperature: 0.0
  max_output_tokens: 2048
  thinking_budget: 0
  workers: 4
  checkpoint_every: 10
  retry_attempts: 2
  min_merge_confidence: 0.8
  max_group_entities: 12
  max_contexts_per_entity: 2
  max_candidate_groups: 300
  enable_similarity_blocks: true
  similarity_threshold: 0.85
  enable_country_state_windows: true
```

## Validation

Local validation is applied after Gemini returns JSON.

Validation checks:

| Check | Behavior |
|---|---|
| Invalid JSON | Retry, then save group to `entity_alignment_errors.json` |
| Unknown member ID | Drop that member from the merge |
| Fewer than 2 valid members | Drop the merge |
| Empty canonical name | Drop the merge |
| Invalid canonical type | Drop the merge |
| Confidence below `0.8` | Reject merge |
| `review_required=true` | Reject merge for automatic alignment |

This means Gemini can suggest uncertain aliases, but only high-confidence non-review merges are applied automatically.

## Quality Assessment

Strengths:

1. All 5866 raw entity mentions are included in the alignment pipeline.
2. Exact normalized merging is deterministic and reproducible.
3. Gemini review completed for 300 prioritized candidate groups with 0 errors.
4. Accepted Gemini merges reduced canonical representatives by 143 more entities.
5. Alias and mention mappings are saved for graph construction.
6. The 300-group cap improves coverage while keeping review targeted and bounded.

Weaknesses:

1. Only 300 fuzzy candidate groups were reviewed by Gemini, not all possible pairs.
2. Some remaining aliases may still be unmerged outside the generated candidate groups.
3. Some accepted merges, especially cross-type country/state names, should be spot-checked before final paper reporting.
4. `Concept` remains the largest aligned type, so graph retrieval may still need concept filtering.

## Should We Review More Than 300 Groups?

Not blindly.

The current 300 groups are a controlled improvement over the initial 150-group run. Increasing the cap or broadening rules further may improve alias coverage, but it may also introduce bad merges.

Recommended next experiment, only if Stage 7 retrieval shows missed aliases:

```yaml
max_candidate_groups: 500
```

Do not increase blindly. Compare:

1. Final aligned entity count.
2. Accepted merge count.
3. Rejected merge count.
4. Manual sample of accepted merges.
5. Whether important aliases like `Mỹ / Hoa Kỳ` improve.

If merge quality remains good, increase again. Do not jump to all groups without quality review.
